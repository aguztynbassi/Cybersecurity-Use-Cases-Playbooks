# File Operations via Windows Administrative Shares

## Description
Alert generated by the `File Operations via Windows Administrative Shares` detection. Detects attempts to copy, move, or otherwise interact with files located on Windows administrative network shares (e.g., `C$`, `ADMIN$`, `IPC$`, `D$`). Adversaries frequently leverage these shares for lateral movement, malware staging, and data exfiltration by directly accessing them via UNC paths (`\\hostname\C$`). This is a common technique as these shares are often accessible with administrative credentials obtained during compromise. The alert must be reviewed by the SOC to validate its legitimacy, scope, affected asset, and potential impact.

## Objective
Detect and prioritize potential malicious, anomalous, or unauthorized activity related to Windows host, enabling the SOC to initiate a structured investigation, reduce operational risk, and activate containment procedures when indicators of compromise are identified.

## Logic
The detection is triggered by the `File Operations via Windows Administrative Shares` rule. The prioritization logic should consider severity, asset criticality, event recurrence, network source/destination, involved identity, platform, and correlated activity in supporting data sources.

Patterns or conditions to validate:

- Exact match of the detection name/signature with this use case.
- Severity equal to or above the SOC-defined threshold.
- Production, critical, publicly exposed, or sensitive-data asset.
- IP address, domain, user, process, or resource not recognized by the asset/account owner.
- Logs or telemetry from the supporting data sources occurring close to the first or last observed event.
- Sensitive changes following the event, such as permission changes, new persistence, credential use, logging changes, public exposure, command execution, or data access.

## Threat
- **Primary Threat:** Command and Control.
- **Family or Mechanism:** File Operations via Windows Administrative Shares.
- Detects attempts to copy, move, or otherwise interact with files located on Windows administrative network shares (e.g., `C$`, `ADMIN$`, `IPC$`, `D$`). Adversaries frequently leverage these shares for lateral movement, malware staging, and data exfiltration by directly accessing them via UNC paths (`\\hostname\C$`). This is a common technique as these shares are often accessible with administrative credentials obtained during compromise. The analyst should consider credential compromise, malware infection, policy violation, misconfiguration, or legitimate administrative activity depending on the technical context of the alert.
- **Data Sources:** Windows Security/System Event Logs, Sysmon, EDR telemetry, PowerShell script-block logging.

## Investigation Sources
- **Detection Details:** rule/detection name, severity, affected host/user/resource, first and last observed time, recurrence count.
- **Identity and Access Logs:** authentication events, session/token details, source IP, user agent, and any related administrative actions.
- **Network Logs:** source/destination IP, port, protocol, country, ASN, and transferred bytes where applicable to this detection.
- **Asset/Resource Configuration:** owner, criticality, exposure, patch level, and any security-control configuration relevant to the finding.
- Operational validation with the resource owner, platform team, or application owner to confirm whether the activity was expected.

## Investigation

Mandatory 5W Questions:

- **Who:** Which user, host, service account, process, or external actor is involved?
- **What:** What action was observed, and what asset was affected? Was there access, execution, a configuration change, network communication, or an authentication attempt?
- **When:** When did the first and last observations occur? Did the activity take place outside expected business hours or near another change?
- **Where:** From which host, IP address, country, ASN, or platform did the activity originate?
- **Why:** Is there an operational justification, approved automation, authorized testing activity, or planned change that explains the event?

## Detailed Checklist for Analysts Reviewing the Alert

- Detection/rule name, severity, affected host, user, or resource, and the platform/category it was raised on.
- Involved identity: username, service account, process owner, or the external source identified in the alert.
- Source and destination details available for this alert (IP, domain, port, protocol, country, ASN) where applicable.
- First and last observed event, frequency, and recurrence within the analysis period.
- Sensitive follow-on actions, such as privilege changes, new persistence mechanisms, log tampering, or data access.
- Relationship with other alerts, EDR detections, SIEM correlations, or existing tickets for the same host/user.
- Confirmation with the owner regarding expected activity, approved automation, authorized testing, or unknown behavior.
- Specific fields referenced by this detection's own alert template:
  - `Timestamp` - when the event occurred
  - `EventID` - the source log's event ID
  - `Image` - the executable image involved
  - `CommandLine` - the full command line observed
  - `ParentImage` - the parent process's executable image
  - `User` - the user account involved
  - `ComputerName` - the affected host
  - `ProcessGuid` - the process's unique identifier (Sysmon GUID)

## Evidence for Determination

### False Positives

- The `File Operations via Windows Administrative Shares` rule has not yet been tuned to this environment and is matching a legitimate, documented pattern - confirm with the asset/account owner before escalating.
- A security tool, EDR agent, or sandbox deliberately connected to a known-bad indicator as part of signature testing or detonation analysis.
- The destination was recently reassigned by a hosting provider and no longer hosts malicious infrastructure.
- An approved IT operations or configuration-management tool legitimately connects to or executes commands on other hosts as part of its documented function.

### True Positives

- This is a common technique as these shares are often accessible with administrative credentials obtained during compromise.
- The host or account is communicating at a regular interval with infrastructure on an active threat-intelligence list, with no legitimate business reason to do so.
- The communication coincides with an unexplained process, scheduled task, or new credential usage on the same host.
- Multiple internal hosts begin communicating with the same external destination in a short window.
- The connecting identity or host has no legitimate operational relationship with the target, and the action follows a known lateral-movement technique.
- The same technique is observed spreading to multiple hosts in a short window.

### True Negatives

- The destination is an approved, documented integration or vendor endpoint.
- The activity matches an approved administrative or orchestration tool's documented behavior.

### False Negatives

- The C2 channel is routed through a reputable CDN or cloud provider (domain fronting), blending in with legitimate traffic.
- The beacon interval is randomized and infrequent enough to stay below this detection's threshold.
- The attacker moves laterally using already-trusted, legitimate administrative channels that closely mimic normal IT operations.

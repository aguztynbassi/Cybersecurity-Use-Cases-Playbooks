# Unsecured Credentials in Files Detected

## Description
Alert generated by the `Unsecured Credentials in Files Detected` detection. Detects attempts by adversaries to search for insecurely stored credentials within files on local file systems and accessible network shares. This involves using command-line search utilities like `findstr.exe`, PowerShell's `Select-String`, or other tools to look for keywords such as "password," "cred," "secret," or specific file extensions (e.g., `.config`, `.txt`, `.xml`, `.ini`). This is a common method within the Credential Access tactic to discover plaintext credentials, hashes, or sensitive configuration data. The alert must be reviewed by the SOC to validate its legitimacy, scope, affected asset, and potential impact.

## Objective
Detect and prioritize potential malicious, anomalous, or unauthorized activity related to Windows host, enabling the SOC to initiate a structured investigation, reduce operational risk, and activate containment procedures when indicators of compromise are identified.

## Logic
The detection is triggered by the `Unsecured Credentials in Files Detected` rule. The prioritization logic should consider severity, asset criticality, event recurrence, network source/destination, involved identity, platform, and correlated activity in supporting data sources.

Patterns or conditions to validate:

- Exact match of the detection name/signature with this use case.
- Severity equal to or above the SOC-defined threshold.
- Production, critical, publicly exposed, or sensitive-data asset.
- IP address, domain, user, process, or resource not recognized by the asset/account owner.
- Logs or telemetry from the supporting data sources occurring close to the first or last observed event.
- Sensitive changes following the event, such as permission changes, new persistence, credential use, logging changes, public exposure, command execution, or data access.

## Investigation

Mandatory 5W Questions:

- **Who:** Which user, host, service account, process, or external actor is involved?
- **What:** What action was observed, and what asset was affected? Was there access, execution, a configuration change, network communication, or an authentication attempt?
- **When:** When did the first and last observations occur? Did the activity take place outside expected business hours or near another change?
- **Where:** From which host, IP address, country, ASN, or platform did the activity originate?
- **Why:** Is there an operational justification, approved automation, authorized testing activity, or planned change that explains the event?

## Detailed Checklist for Analysts Reviewing the Alert

- Detection/rule name, severity, affected host, user, or resource, and the platform/category it was raised on.
- Involved identity: username, service account, process owner, or the external source identified in the alert.
- Source and destination details available for this alert (IP, domain, port, protocol, country, ASN) where applicable.
- First and last observed event, frequency, and recurrence within the analysis period.
- Sensitive follow-on actions, such as privilege changes, new persistence mechanisms, log tampering, or data access.
- Relationship with other alerts, EDR detections, SIEM correlations, or existing tickets for the same host/user.
- Confirmation with the owner regarding expected activity, approved automation, authorized testing, or unknown behavior.
- Specific fields referenced by this detection's own alert template:
  - `Timestamp` - when the event occurred
  - `EventID` - the source log's event ID
  - `Image` - the executable image involved
  - `CommandLine` - the full command line observed
  - `ParentImage` - the parent process's executable image
  - `User` - the user account involved
  - `ComputerName` - the affected host
  - `ProcessGuid` - the process's unique identifier (Sysmon GUID)

## Evidence for Determination

### False Positives

- The `Unsecured Credentials in Files Detected` rule has not yet been tuned to this environment and is matching a legitimate, documented pattern - confirm with the asset/account owner before escalating.
- A legitimate user forgot their password or mistyped credentials; failed attempts stop after a normal self-correction.
- An approved credential-management tool or migration script is reading/validating credentials as part of its documented function.

### True Positives

- This is a common method within the Credential Access tactic to discover plaintext credentials, hashes, or sensitive configuration data.
- The attempt pattern (volume, source diversity, targeted usernames) is inconsistent with normal user behavior and matches brute-force, spraying, or credential-dumping tradecraft.
- A successful authentication follows a string of failures, or succeeds from a source/location with no history for this account.
- The credential material or technique matches a known credential-access tool.

### True Negatives

- The pattern is confirmed to be normal user error or an approved automated process.

### False Negatives

- The attacker already possesses valid, previously-stolen credentials and succeeds on the first attempt, leaving no failed-attempt pattern to detect.
- Credential material is harvested through a channel this detection does not monitor (e.g., a phishing page hosted outside the organization).

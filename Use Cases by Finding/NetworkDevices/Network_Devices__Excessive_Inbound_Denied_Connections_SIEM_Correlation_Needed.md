# Excessive Inbound Denied Connections (SIEM Correlation Needed)

## Description
Alert generated by the `Excessive Inbound Denied Connections (SIEM Correlation Needed)` detection. Detects an excessive number of inbound network connection attempts explicitly denied or blocked by a firewall or IDS/IPS, originating from the same source IP and targeting the same internal destination IP within a short timeframe. This is a strong indicator of active malicious reconnaissance, port scanning, or brute-force attacks. The alert must be reviewed by the SOC to validate its legitimacy, scope, affected asset, and potential impact.

## Objective
Detect and prioritize potential malicious, anomalous, or unauthorized activity related to network device (firewall, router, switch, or IDS/IPS sensor), enabling the SOC to initiate a structured investigation, reduce operational risk, and activate containment procedures when indicators of compromise are identified.

## Logic
The detection is triggered by the `Excessive Inbound Denied Connections (SIEM Correlation Needed)` rule. The prioritization logic should consider severity, asset criticality, event recurrence, network source/destination, involved identity, platform, and correlated activity in supporting data sources.

Patterns or conditions to validate:

- Exact match of the detection name/signature with this use case.
- Severity equal to or above the SOC-defined threshold.
- Production, critical, publicly exposed, or sensitive-data asset.
- IP address, domain, user, process, or resource not recognized by the asset/account owner.
- Logs or telemetry from the supporting data sources occurring close to the first or last observed event.
- Sensitive changes following the event, such as permission changes, new persistence, credential use, logging changes, public exposure, command execution, or data access.

## Investigation

Mandatory 5W Questions:

- **Who:** Which user, host, service account, process, or external actor is involved?
- **What:** What action was observed, and what asset was affected? Was there access, execution, a configuration change, network communication, or an authentication attempt?
- **When:** When did the first and last observations occur? Did the activity take place outside expected business hours or near another change?
- **Where:** From which host, IP address, country, ASN, or platform did the activity originate?
- **Why:** Is there an operational justification, approved automation, authorized testing activity, or planned change that explains the event?

## Detailed Checklist for Analysts Reviewing the Alert

- Detection/rule name, severity, affected host, user, or resource, and the platform/category it was raised on.
- Involved identity: username, service account, process owner, or the external source identified in the alert.
- Source and destination details available for this alert (IP, domain, port, protocol, country, ASN) where applicable.
- First and last observed event, frequency, and recurrence within the analysis period.
- Sensitive follow-on actions, such as privilege changes, new persistence mechanisms, log tampering, or data access.
- Relationship with other alerts, EDR detections, SIEM correlations, or existing tickets for the same host/user.
- Confirmation with the owner regarding expected activity, approved automation, authorized testing, or unknown behavior.
- Specific fields referenced by this detection's own alert template:
  - `Timestamp` - when the event occurred
  - `SourceIp` - the source IP address
  - `DestinationIp` - the destination IP address
  - `DestinationPort` - the destination port
  - `Protocol` - the network protocol observed
  - `Action` - the action taken (allowed/denied/etc.)
  - `Direction` - the direction field referenced by this alert
  - `Application` - the application field referenced by this alert

## Evidence for Determination

### False Positives

- The `Excessive Inbound Denied Connections (SIEM Correlation Needed)` rule has not yet been tuned to this environment and is matching a legitimate, documented pattern - confirm with the asset/account owner before escalating.
- A legitimate administrative, monitoring, or inventory tool performs the same enumeration as part of its normal, approved function.
- A new, approved automation or audit process is running for the first time and has not yet been accounted for.
- An authorized vulnerability scan, asset-discovery tool, or security assessment generated the activity from an approved, documented source.
- A partner, customer, or monitoring integration with a legitimate reason to probe the asset triggered the detection.

### True Positives

- This is a strong indicator of active malicious reconnaissance, port scanning, or brute-force attacks.
- The enumeration is performed by an identity or process with no legitimate reason to need this information.
- It follows another compromise indicator on the same host or account.
- The scope or depth of enumeration goes well beyond what any legitimate tool on this host would need.
- The source has no documented business relationship with the organization and the activity matches known reconnaissance tradecraft.
- The reconnaissance is followed by an exploitation attempt or a successful connection shortly after.

### True Negatives

- The activity is confirmed to be an approved, scheduled audit or inventory process.
- The activity is confirmed to come from an approved, scheduled security-scanning provider.

### False Negatives

- The attacker already has the information from a prior reconnaissance phase or from an external source, so no new enumeration activity is generated.
- Discovery is performed through an API or method this detection does not cover.
- The activity is paced slowly enough (low-and-slow) to stay under the detection's volumetric threshold.
- The actor already has the information being enumerated from a prior, undetected reconnaissance pass.

# Inbound RDP Connection from External Source

## Description
Alert generated by the `Inbound RDP Connection from External Source` detection. Detects inbound Remote Desktop Protocol (RDP) connections initiated from external IP addresses targeting internal systems. Direct exposure of RDP to the internet is a significant security vulnerability, frequently exploited for initial access, lateral movement, and persistent access. The alert must be reviewed by the SOC to validate its legitimacy, scope, affected asset, and potential impact.

## Objective
Detect and prioritize potential malicious, anomalous, or unauthorized activity related to network device (firewall, router, switch, or IDS/IPS sensor), enabling the SOC to initiate a structured investigation, reduce operational risk, and activate containment procedures when indicators of compromise are identified.

## Logic
The detection is triggered by the `Inbound RDP Connection from External Source` rule. The prioritization logic should consider severity, asset criticality, event recurrence, network source/destination, involved identity, platform, and correlated activity in supporting data sources.

Patterns or conditions to validate:

- Exact match of the detection name/signature with this use case.
- Severity equal to or above the SOC-defined threshold.
- Production, critical, publicly exposed, or sensitive-data asset.
- IP address, domain, user, process, or resource not recognized by the asset/account owner.
- Logs or telemetry from the supporting data sources occurring close to the first or last observed event.
- Sensitive changes following the event, such as permission changes, new persistence, credential use, logging changes, public exposure, command execution, or data access.

- **Family or Mechanism:** Inbound RDP Connection from External Source.
- Detects inbound Remote Desktop Protocol (RDP) connections initiated from external IP addresses targeting internal systems. Direct exposure of RDP to the internet is a significant security vulnerability, frequently exploited for initial access, lateral movement, and persistent access. The analyst should consider credential compromise, malware infection, policy violation, misconfiguration, or legitimate administrative activity depending on the technical context of the alert.
- **Data Sources:** firewall/IDS/IPS logs, NetFlow/IPFIX, DNS logs, proxy logs.

## Investigation Sources
- **Detection Details:** rule/detection name, severity, affected host/user/resource, first and last observed time, recurrence count.
- **Identity and Access Logs:** authentication events, session/token details, source IP, user agent, and any related administrative actions.

- **Asset/Resource Configuration:** owner, criticality, exposure, patch level, and any security-control configuration relevant to the finding.

## Investigation

Mandatory 5W Questions:

- **Who:** Which user, host, service account, process, or external actor is involved?
- **What:** What action was observed, and what asset was affected? Was there access, execution, a configuration change, network communication, or an authentication attempt?
- **When:** When did the first and last observations occur? Did the activity take place outside expected business hours or near another change?
- **Where:** From which host, IP address, country, ASN, or platform did the activity originate?
- **Why:** Is there an operational justification, approved automation, authorized testing activity, or planned change that explains the event?

## Detailed Checklist for Analysts Reviewing the Alert

- Detection/rule name, severity, affected host, user, or resource, and the platform/category it was raised on.
- Involved identity: username, service account, process owner, or the external source identified in the alert.
- Source and destination details available for this alert (IP, domain, port, protocol, country, ASN) where applicable.
- First and last observed event, frequency, and recurrence within the analysis period.
- Sensitive follow-on actions, such as privilege changes, new persistence mechanisms, log tampering, or data access.
- Relationship with other alerts, EDR detections, SIEM correlations, or existing tickets for the same host/user.
- Confirmation with the owner regarding expected activity, approved automation, authorized testing, or unknown behavior.
- Specific fields referenced by this detection's own alert template:
  - `Timestamp` - when the event occurred
  - `SourceIp` - the source IP address
  - `DestinationIp` - the destination IP address
  - `DestinationPort` - the destination port
  - `Protocol` - the network protocol observed
  - `Direction` - the direction field referenced by this alert
  - `Action` - the action taken (allowed/denied/etc.)
  - `User` - the user account involved

## Evidence for Determination

### False Positives

- The `Inbound RDP Connection from External Source` rule has not yet been tuned to this environment and is matching a legitimate, documented pattern - confirm with the asset/account owner before escalating.
- An approved IT operations or configuration-management tool legitimately connects to or executes commands on other hosts as part of its documented function.

### True Positives

- Direct exposure of RDP to the internet is a significant security vulnerability, frequently exploited for initial access, lateral movement, and persistent access.
- The connecting identity or host has no legitimate operational relationship with the target, and the action follows a known lateral-movement technique.
- The same technique is observed spreading to multiple hosts in a short window.
- It follows a credential-theft or initial-access indicator on the originating host.

### True Negatives

- The activity matches an approved administrative or orchestration tool's documented behavior.

### False Negatives

- The attacker moves laterally using already-trusted, legitimate administrative channels that closely mimic normal IT operations.

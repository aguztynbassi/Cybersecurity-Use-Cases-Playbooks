# Persistence: Winlogon Helper DLL or Shell Modification Detected

## Description
Alert generated by the `Persistence: Winlogon Helper DLL or Shell Modification Detected` detection. Detects suspicious modifications to Winlogon registry keys (such as Shell, Userinit, or Notify). Adversaries use these keys to ensure their malicious code runs automatically every time a user logs into the system. Since Winlogon is a critical Windows process, abusing its components enables robust persistence and execution with high privileges. The alert must be reviewed by the SOC to validate its legitimacy, scope, affected asset, and potential impact.

## Objective
Detect and prioritize potential malicious, anomalous, or unauthorized activity related to Windows host, enabling the SOC to initiate a structured investigation, reduce operational risk, and activate containment procedures when indicators of compromise are identified.

## Logic
The detection is triggered by the `Persistence: Winlogon Helper DLL or Shell Modification Detected` rule. The prioritization logic should consider severity, asset criticality, event recurrence, network source/destination, involved identity, platform, and correlated activity in supporting data sources.

Patterns or conditions to validate:

- Exact match of the detection name/signature with this use case.
- Severity equal to or above the SOC-defined threshold.
- Production, critical, publicly exposed, or sensitive-data asset.
- IP address, domain, user, process, or resource not recognized by the asset/account owner.
- Logs or telemetry from the supporting data sources occurring close to the first or last observed event.
- Sensitive changes following the event, such as permission changes, new persistence, credential use, logging changes, public exposure, command execution, or data access.

## Evidence for Determination

### False Positives

- The `Persistence: Winlogon Helper DLL or Shell Modification Detected` rule has not yet been tuned to this environment and is matching a legitimate, documented pattern - confirm with the asset/account owner before escalating.
- An approved administrator or automation legitimately required and obtained elevated privileges through a documented process.
- A security-testing tool intentionally exercised the privilege-escalation path as part of an approved assessment.
- A legitimate software installer, IT management tool, or approved automation created the persistence mechanism as part of its normal function.
- An administrator intentionally configured the mechanism (service, scheduled task, startup entry) for a documented operational reason.

### True Positives

- Since Winlogon is a critical Windows process, abusing its components enables robust persistence and execution with high privileges.
- An account or process gains privileges it does not normally hold, with no corresponding approval or ticket.
- The elevation is followed by actions normally reserved for administrators.
- The technique used matches a known, documented privilege-escalation exploit or misconfiguration abuse.
- The persistence mechanism points to an unfamiliar binary, script, or location with no legitimate business purpose.
- The mechanism was created shortly after another suspicious event on the same host (new login, exploitation, suspicious download).

### True Negatives

- The elevation matches an approved administrative workflow.
- The change is tied to an approved deployment or administrative action.

### False Negatives

- The attacker already holds sufficient privileges from an earlier, undetected compromise, so no escalation event occurs for this detection to catch.
- Escalation is achieved through a legitimate-looking, pre-existing misconfiguration rather than an exploit this detection watches for.
- The persistence mechanism is deliberately disguised to resemble a legitimate, commonly-seen entry.
- Persistence is established through a technique this detection does not specifically cover.

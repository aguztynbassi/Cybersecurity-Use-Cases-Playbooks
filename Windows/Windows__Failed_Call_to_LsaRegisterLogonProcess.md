# Failed Call to LsaRegisterLogonProcess()

## Description
Alert generated by the `Failed Call to LsaRegisterLogonProcess()` detection. Detects a failed attempt to call the privileged Windows function `LsaRegisterLogonProcess()`. This can indicate unauthorized attempts to interact with the Local Security Authority (LSA), often as part of a privilege escalation attempt, credential access, or a bypass of security controls. The specific failure reason `%%1794` confirms the process lacked the necessary privileges for this action. The alert must be reviewed by the SOC to validate its legitimacy, scope, affected asset, and potential impact.

## Objective
Detect and prioritize potential malicious, anomalous, or unauthorized activity related to Windows host, enabling the SOC to initiate a structured investigation, reduce operational risk, and activate containment procedures when indicators of compromise are identified.

## Logic
The detection is triggered by the `Failed Call to LsaRegisterLogonProcess()` rule. The prioritization logic should consider severity, asset criticality, event recurrence, network source/destination, involved identity, platform, and correlated activity in supporting data sources.

Patterns or conditions to validate:

- Exact match of the detection name/signature with this use case.
- Severity equal to or above the SOC-defined threshold.
- Production, critical, publicly exposed, or sensitive-data asset.
- IP address, domain, user, process, or resource not recognized by the asset/account owner.
- Logs or telemetry from the supporting data sources occurring close to the first or last observed event.
- Sensitive changes following the event, such as permission changes, new persistence, credential use, logging changes, public exposure, command execution, or data access.

## Evidence for Determination

### False Positives

- The `Failed Call to LsaRegisterLogonProcess()` rule has not yet been tuned to this environment and is matching a legitimate, documented pattern - confirm with the asset/account owner before escalating.
- An approved IT operations or configuration-management tool legitimately connects to or executes commands on other hosts as part of its documented function.
- An approved administrator or automation legitimately required and obtained elevated privileges through a documented process.
- A security-testing tool intentionally exercised the privilege-escalation path as part of an approved assessment.

### True Positives

- The specific failure reason `%%1794` confirms the process lacked the necessary privileges for this action.
- The connecting identity or host has no legitimate operational relationship with the target, and the action follows a known lateral-movement technique.
- The same technique is observed spreading to multiple hosts in a short window.
- It follows a credential-theft or initial-access indicator on the originating host.
- An account or process gains privileges it does not normally hold, with no corresponding approval or ticket.
- The elevation is followed by actions normally reserved for administrators.

### True Negatives

- The activity matches an approved administrative or orchestration tool's documented behavior.
- The elevation matches an approved administrative workflow.

### False Negatives

- The attacker moves laterally using already-trusted, legitimate administrative channels that closely mimic normal IT operations.
- The attacker already holds sufficient privileges from an earlier, undetected compromise, so no escalation event occurs for this detection to catch.
- Escalation is achieved through a legitimate-looking, pre-existing misconfiguration rather than an exploit this detection watches for.

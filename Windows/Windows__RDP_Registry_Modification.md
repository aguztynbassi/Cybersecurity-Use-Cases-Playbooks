# RDP Registry Modification Detected

## Description
Alert generated by the `RDP Registry Modification Detected` detection. Detects the modification of specific registry keys to enable Remote Desktop (RDP) connections and disable Network Level Authentication (NLA). Attackers make these changes to open remote-access vectors on systems that were previously protected, or to facilitate lateral movement within the network. The alert must be reviewed by the SOC to validate its legitimacy, scope, affected asset, and potential impact.

## Objective
Detect and prioritize potential malicious, anomalous, or unauthorized activity related to Windows host, enabling the SOC to initiate a structured investigation, reduce operational risk, and activate containment procedures when indicators of compromise are identified.

## Logic
The detection is triggered by the `RDP Registry Modification Detected` rule. The prioritization logic should consider severity, asset criticality, event recurrence, network source/destination, involved identity, platform, and correlated activity in supporting data sources.

Patterns or conditions to validate:

- Exact match of the detection name/signature with this use case.
- Severity equal to or above the SOC-defined threshold.
- Production, critical, publicly exposed, or sensitive-data asset.
- IP address, domain, user, process, or resource not recognized by the asset/account owner.
- Logs or telemetry from the supporting data sources occurring close to the first or last observed event.
- Sensitive changes following the event, such as permission changes, new persistence, credential use, logging changes, public exposure, command execution, or data access.

## Investigation

Mandatory 5W Questions:

- **Who:** Which user, host, service account, process, or external actor is involved?
- **What:** What action was observed, and what asset was affected? Was there access, execution, a configuration change, network communication, or an authentication attempt?
- **When:** When did the first and last observations occur? Did the activity take place outside expected business hours or near another change?
- **Where:** From which host, IP address, country, ASN, or platform did the activity originate?
- **Why:** Is there an operational justification, approved automation, authorized testing activity, or planned change that explains the event?

## Detailed Checklist for Analysts Reviewing the Alert

- Detection/rule name, severity, affected host, user, or resource, and the platform/category it was raised on.
- Involved identity: username, service account, process owner, or the external source identified in the alert.
- Source and destination details available for this alert (IP, domain, port, protocol, country, ASN) where applicable.
- First and last observed event, frequency, and recurrence within the analysis period.
- Sensitive follow-on actions, such as privilege changes, new persistence mechanisms, log tampering, or data access.
- Relationship with other alerts, EDR detections, SIEM correlations, or existing tickets for the same host/user.
- Confirmation with the owner regarding expected activity, approved automation, authorized testing, or unknown behavior.
- Specific fields referenced by this detection's own alert template:
  - `host` - the affected host
  - `target_object` - the registry or object path affected
  - `user` - the user account involved

## Evidence for Determination

### False Positives

- The `RDP Registry Modification Detected` rule has not yet been tuned to this environment and is matching a legitimate, documented pattern - confirm with the asset/account owner before escalating.
- A legitimate software installer, IT management tool, or approved automation created the persistence mechanism as part of its normal function.
- An administrator intentionally configured the mechanism (service, scheduled task, startup entry) for a documented operational reason.
- A platform or security administrator intentionally disabled or reconfigured the control as part of an approved maintenance or migration task, with change records on file.

### True Positives

- Attackers make these changes to open remote-access vectors on systems that were previously protected, or to facilitate lateral movement within the network.
- The persistence mechanism points to an unfamiliar binary, script, or location with no legitimate business purpose.
- The mechanism was created shortly after another suspicious event on the same host (new login, exploitation, suspicious download).
- No change ticket or administrator acknowledges the change when the SOC follows up.
- A security control (logging, AV/EDR, firewall rule, audit policy) was disabled or weakened by an identity with no administrative justification for managing it.
- The change occurs immediately before or after other suspicious activity that the disabled control would otherwise have captured.

### True Negatives

- The change is tied to an approved deployment or administrative action.
- The change is tied to an approved, documented administrative action.

### False Negatives

- The persistence mechanism is deliberately disguised to resemble a legitimate, commonly-seen entry.
- Persistence is established through a technique this detection does not specifically cover.
- The attacker impairs a different control not covered by this specific detection, or avoids touching monitored settings entirely.
- The control is disabled only momentarily, in a window too short to generate a reliable signal.

# Suspicious Scheduled Task Creation

## Description
Alert generated by the `Suspicious Scheduled Task Creation` detection. The creation of a scheduled task with suspicious characteristics has been detected, which could indicate an attacker establishing persistence or executing malicious code. The alert must be reviewed by the SOC to validate its legitimacy, scope, affected asset, and potential impact.

## Objective
Detect and prioritize potential malicious, anomalous, or unauthorized activity related to Windows host, enabling the SOC to initiate a structured investigation, reduce operational risk, and activate containment procedures when indicators of compromise are identified.

## Logic
The detection is triggered by the `Suspicious Scheduled Task Creation` rule. The prioritization logic should consider severity, asset criticality, event recurrence, network source/destination, involved identity, platform, and correlated activity in supporting data sources.

Patterns or conditions to validate:

- Exact match of the detection name/signature with this use case.
- Severity equal to or above the SOC-defined threshold.
- Production, critical, publicly exposed, or sensitive-data asset.
- IP address, domain, user, process, or resource not recognized by the asset/account owner.
- Logs or telemetry from the supporting data sources occurring close to the first or last observed event.
- Sensitive changes following the event, such as permission changes, new persistence, credential use, logging changes, public exposure, command execution, or data access.

## MITRE ATT&CK

- T1053 - Scheduled Task/Job (Execution, Persistence, Privilege Escalation)

## Threat
- **Primary Threat:** Privilege Escalation.
- **Family or Mechanism:** Suspicious Scheduled Task Creation.
- The creation of a scheduled task with suspicious characteristics has been detected, which could indicate an attacker establishing persistence or executing malicious code. The analyst should consider credential compromise, malware infection, policy violation, misconfiguration, or legitimate administrative activity depending on the technical context of the alert.
- **Data Sources:** Windows Security/System Event Logs, Sysmon, EDR telemetry, PowerShell script-block logging.

## Investigation Sources
- **Detection Details:** rule/detection name, severity, affected host/user/resource, first and last observed time, recurrence count.
- **Identity and Access Logs:** authentication events, session/token details, source IP, user agent, and any related administrative actions.
- **Network Logs:** source/destination IP, port, protocol, country, ASN, and transferred bytes where applicable to this detection.
- **Asset/Resource Configuration:** owner, criticality, exposure, patch level, and any security-control configuration relevant to the finding.
- Operational validation with the resource owner, platform team, or application owner to confirm whether the activity was expected.

## Investigation

Mandatory 5W Questions:

- **Who:** Which user, host, service account, process, or external actor is involved?
- **What:** What action was observed, and what asset was affected? Was there access, execution, a configuration change, network communication, or an authentication attempt?
- **When:** When did the first and last observations occur? Did the activity take place outside expected business hours or near another change?
- **Where:** From which host, IP address, country, ASN, or platform did the activity originate?
- **Why:** Is there an operational justification, approved automation, authorized testing activity, or planned change that explains the event?

## Detailed Checklist for Analysts Reviewing the Alert

- Detection/rule name, severity, affected host, user, or resource, and the platform/category it was raised on.
- Involved identity: username, service account, process owner, or the external source identified in the alert.
- Source and destination details available for this alert (IP, domain, port, protocol, country, ASN) where applicable.
- First and last observed event, frequency, and recurrence within the analysis period.
- Sensitive follow-on actions, such as privilege changes, new persistence mechanisms, log tampering, or data access.
- Relationship with other alerts, EDR detections, SIEM correlations, or existing tickets for the same host/user.
- Confirmation with the owner regarding expected activity, approved automation, authorized testing, or unknown behavior.
- Specific fields referenced by this detection's own alert template:
  - `Timestamp` - when the event occurred
  - `EventID` - the source log's event ID
  - `TaskName` - the task name field referenced by this alert
  - `TaskCommand` - the task command field referenced by this alert
  - `SubjectUserName` - the identity that performed the action
  - `SubjectDomainName` - the subject domain name field referenced by this alert
  - `ComputerName` - the affected host

## Evidence for Determination

### False Positives

- The `Suspicious Scheduled Task Creation` rule has not yet been tuned to this environment and is matching a legitimate, documented pattern - confirm with the asset/account owner before escalating.
- An approved administrator or automation legitimately required and obtained elevated privileges through a documented process.
- A security-testing tool intentionally exercised the privilege-escalation path as part of an approved assessment.
- A legitimate administrator, script, or scheduled task executed the command/binary as part of approved, documented operations.
- A security or monitoring tool itself performs an action that matches this execution pattern by design.

### True Positives

- The creation of a scheduled task with suspicious characteristics has been detected, which could indicate an attacker establishing persistence or executing malicious code.
- An account or process gains privileges it does not normally hold, with no corresponding approval or ticket.
- The elevation is followed by actions normally reserved for administrators.
- The technique used matches a known, documented privilege-escalation exploit or misconfiguration abuse.
- The executing process, command line, or binary has no legitimate reason to run in this context and matches known attacker tradecraft.
- Execution is followed by further suspicious activity (network connections, new files, privilege changes) on the same host.

### True Negatives

- The elevation matches an approved administrative workflow.
- The execution is confirmed to be part of an approved script, deployment, or administrative task.

### False Negatives

- The attacker already holds sufficient privileges from an earlier, undetected compromise, so no escalation event occurs for this detection to catch.
- Escalation is achieved through a legitimate-looking, pre-existing misconfiguration rather than an exploit this detection watches for.
- The payload executes through a technique or LOLBin not yet covered by this detection's specific logic.
- The malicious code runs entirely in memory or is obfuscated enough to avoid matching the detection's pattern.

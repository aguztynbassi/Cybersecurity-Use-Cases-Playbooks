# Suspect Svchost Memory Access

## Description
Alert generated by the `Suspect Svchost Memory Access` detection. Detects suspicious memory access to `svchost.exe`. Adversaries may inject malicious code into `svchost.exe` to execute code, evade security defenses, and potentially disrupt services. This is a common defense evasion and privilege escalation technique. The alert must be reviewed by the SOC to validate its legitimacy, scope, affected asset, and potential impact.

## Objective
Detect and prioritize potential malicious, anomalous, or unauthorized activity related to Windows host, enabling the SOC to initiate a structured investigation, reduce operational risk, and activate containment procedures when indicators of compromise are identified.

## Logic
The detection is triggered by the `Suspect Svchost Memory Access` rule. The prioritization logic should consider severity, asset criticality, event recurrence, network source/destination, involved identity, platform, and correlated activity in supporting data sources.

Patterns or conditions to validate:

- Exact match of the detection name/signature with this use case.
- Severity equal to or above the SOC-defined threshold.
- Production, critical, publicly exposed, or sensitive-data asset.
- IP address, domain, user, process, or resource not recognized by the asset/account owner.
- Logs or telemetry from the supporting data sources occurring close to the first or last observed event.
- Sensitive changes following the event, such as permission changes, new persistence, credential use, logging changes, public exposure, command execution, or data access.

## Investigation

Mandatory 5W Questions:

- **Who:** Which user, host, service account, process, or external actor is involved?
- **What:** What action was observed, and what asset was affected? Was there access, execution, a configuration change, network communication, or an authentication attempt?
- **When:** When did the first and last observations occur? Did the activity take place outside expected business hours or near another change?
- **Where:** From which host, IP address, country, ASN, or platform did the activity originate?
- **Why:** Is there an operational justification, approved automation, authorized testing activity, or planned change that explains the event?

## Evidence for Determination

### False Positives

- The `Suspect Svchost Memory Access` rule has not yet been tuned to this environment and is matching a legitimate, documented pattern - confirm with the asset/account owner before escalating.
- A platform or security administrator intentionally disabled or reconfigured the control as part of an approved maintenance or migration task, with change records on file.

### True Positives

- This is a common defense evasion and privilege escalation technique.
- A security control (logging, AV/EDR, firewall rule, audit policy) was disabled or weakened by an identity with no administrative justification for managing it.
- The change occurs immediately before or after other suspicious activity that the disabled control would otherwise have captured.
- No change ticket or administrator acknowledges the modification.

### True Negatives

- The change is tied to an approved, documented administrative action.

### False Negatives

- The attacker impairs a different control not covered by this specific detection, or avoids touching monitored settings entirely.
- The control is disabled only momentarily, in a window too short to generate a reliable signal.
